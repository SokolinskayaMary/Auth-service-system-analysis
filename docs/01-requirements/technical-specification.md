# Техническое задание

**Тема проекта:** Разработка системы аутентификации и авторизации для веб-приложения и мобильного приложения

# 1. Введение

Документ определяет, **что должна делать** система аутентификации и авторизации, для каких пользователей она предназначена, какие ограничения установлены и как проверить результат работы. Система обеспечивает единый вход для веб-приложения и мобильных приложений и не допускает пользователя к защищённым действиям без необходимых прав.

# 2. Назначение

**Цель разработки** — предоставить пользователю безопасный и удобный доступ к одной учётной записи из веб-приложения и мобильного приложения.

Система предназначена для регистрации по номеру телефона, входа с паролем и дополнительным SMS-кодом, управления действующими сеансами, восстановления пароля, ограничения доступа по роли и администрирования учётных записей. Одновременно одному пользователю разрешено использовать не более трёх подключённых устройств.

# 3. Область применения

Систему используют обычный пользователь (USER), администратор (ADMIN), веб-клиент и мобильные приложения Android/iOS. Защищённые backend-сервисы обращаются к результатам аутентификации и применяют права доступа.

Внешние взаимодействия: SMS-провайдер для доставки одноразовых кодов, Google и VK ID — для входа с **ранее привязанной** внешней учётной записью.

**Включено в объём:** регистрация по телефону, SMS-подтверждение, вход по телефону и паролю, настраиваемая SMS-2FA, серверные сессии, access/refresh-токены, управление устройствами, RBAC, блокировка/разблокировка, восстановление пароля, вход через ранее привязанные Google/VK ID.

# 4. Определения и сокращения

| **Термин**     | **Простое определение**                                                                            |
|----------------|----------------------------------------------------------------------------------------------------|
| Идентификация  | Пользователь указывает номер телефона своей учётной записи.                                        |
| Аутентификация | Система проверяет, действительно ли человек владеет учётной записью.                               |
| Авторизация    | Система проверяет, разрешено ли уже вошедшему пользователю конкретное действие.                    |
| 2FA            | Дополнительное подтверждение входа одноразовым SMS-кодом после проверки пароля.                    |
| IdP            | Компонент, который хранит учётные записи, проверяет пароль, управляет сессиями и выпускает токены. |
| API Gateway    | Принимает HTTP-запросы, выполняет технические проверки и передаёт их нужному компоненту.           |

| OpenAPI        | Описание доступных запросов, их параметров и ответов.                                              |

# 5. Описание системы

## 5.1. Состав и распределение ответственности

**Web UI/Mobile UI** показывает формы регистрации и входа, отправляет API-запросы, отображает результаты и безопасно работает с выданными токенами.

**API Gateway** принимает HTTPS-запросы, ограничивает частоту обращений, проверяет подпись и срок действия JWT и передаёт запросы в backend. Он не создаёт пользовательские сессии и не выпускает токены.

**Registration Service** руководит регистрацией: проверка номера, начало SMS-проверки и создание учётной записи после подтверждения.

**Verification Service** создаёт и проверяет одноразовые SMS-коды, учитывает попытки и вызывает SMS-провайдера.

**IdP** проверяет пароль и статус пользователя, управляет устройствами и сессиями, хранит безопасные представления секретов, создаёт и обновляет токены. Отдельные Token Service и Session Manager не требуются: это обязанности IdP.

**Защищённый backend** перед выполнением операции проверяет, что сессия действительна, пользователь не заблокирован и его роль позволяет выполнить действие.

## 5.2. Как организована обработка запросов

Регистрация, вход, восстановление пароля и администрирование выполняются через API Gateway. Вход пользователя **не равен** автоматическому разрешению всех действий: после проверки токена защищённый backend отдельно учитывает состояние сессии, статус учётной записи и права роли.

Проверка одноразового кода привязывается к конкретному challenge_id. При успешной регистрации пользователю назначаются роль USER и статус ACTIVE. Для второго фактора и восстановления пароля используются отдельные попытки SMS-подтверждения.

## 5.3. Данные системы

Система хранит сведения о пользователях, паролях в виде стойких хэшей, статусах, ролях и разрешениях, устройствах, сессиях, идентификаторах и состоянии SMS-попыток, а также привязках внешних поставщиков входа. Хранение access JWT целиком не требуется, refresh-токены не сохраняются в открытом виде.

# 6. Требования к функциональности

## 6.1. Регистрация

**FR1-01.** Система должна регистрировать пользователей только по номеру телефона, регистрация по электронной почте не предусмотрена.

**FR1-02.** Система должна проверять, что указанный номер ещё не зарегистрирован, и не допускать появления двух учётных записей с одним номером.

**FR1-03.** Для подтверждения номера система должна отправлять одноразовый пятизначный код по SMS.

**FR1-04.** Для каждой SMS-проверки система должна создавать challenge_id, связывать его с номером телефона и проверять код только в рамках этой попытки.

**FR1-05.** Пользователь должен иметь возможность запросить повторную отправку SMS-кода. Система должна ограничивать частоту отправок до 3-х.

**FR1-06.** Система должна разрешать не более трёх неверных попыток ввода кода в рамках SMS-проверки.

**FR1-07.** После подтверждения номера система должна принимать ФИО, дату рождения, ответ на секретный вопрос, пароль и сведения об устройстве.

**FR-08.** Система должна создавать учётную запись только после подтверждения номера и получения регистрационных данных, новому пользователю назначаются USER и ACTIVE.

**FR1-09.** Повторное использование завершённой SMS-проверки для создания ещё одной учётной записи должно быть запрещено.

**FR1-10.** Секретный вопрос. При регистрации система должна показывать пользователю секретный вопрос и сохранять введённый ответ в защищённом виде. При восстановлении пароля система должна показывать тот же вопрос и проверять введённый ответ.

## 6.2. Вход и подтверждение личности

**FR2-1.** Система должна обеспечивать вход по номеру телефона и паролю.

**FR2-2.** Если пользователь заблокирован (BLOCKED), система должна отказывать ему во входе. Только администратор может снять блокировку.

**FR2-3.** Если пользователь стал неактивным (INACTIVE) из-за отсутствия входов в течение двух месяцев, система должна разрешать ему пройти обычную проверку личности и после успешного входа менять статус на ACTIVE.

**FR2-4.** При включённой 2FA система должна дополнительно запрашивать одноразовый SMS-код, до проверки кода токены доступа выдаваться не должны.

**FR2-5.** Система должна позволять владельцу учётной записи включать и выключать SMS-2FA. Перед выключением система должна повторно проверять личность пользователя.

**FR2-6.** Мобильное приложение должно предоставлять возможность локального быстрого доступа через биометрию устройства или PIN, если устройство и ОС это поддерживают. Биометрические данные серверу не передаются.

## 6.3. Устройства, сессии и токены

**FR3-1.** Система должна разрешать не более трёх **одновременно подключённых устройств** одного пользователя. Подключённым считается устройство с действующей сессией.

**FR3-2.** При успешном входе система должна создавать сессию для устройства и выдавать access JWT и refresh-токен.

**FR3-3.** Пользователь должен иметь возможность просмотреть список своих активных сессий и сведения об устройствах.

**FR3-4.** Пользователь должен иметь возможность завершить свою текущую или выбранную сессию. Завершение чужой сессии запрещено.

**FR3-5.** Система должна обновлять access-токен по действующему refresh-токену без повторного ввода пароля, если сессия остаётся действительной.

**FR3-6.** Если пользователь не проявлял активности более трёх минут, его сессия должна считаться завершённой. Защищённые запросы и обновление токена по такой сессии должны отклоняться.

## 6.4. Авторизация и функции администратора

**FR4-1.** Система должна поддерживать роли USER и ADMIN, одному пользователю назначается одна роль.

**FR4-2.** Для доступа к защищённому действию система должна проверять действительность токена и сессии, статус пользователя и разрешение его роли.

**FR4-3.** Пользователь должен иметь доступ к своему профилю без возможности получить из API пароль, секретный ответ или их хэши.

**FR4-4.** Администратор должен иметь возможность назначить пользователю роль ADMIN и вернуть роль USER.

**FR4-5.** Администратор должен иметь возможность заблокировать пользователя и снять административную блокировку. Обычный пользователь не должен иметь возможность выполнять эти действия.

## 6.5. Восстановление пароля и внешний вход

**FR5-1.** При восстановлении пароля система должна отправлять одноразовый SMS-код на номер, связанный с учётной записью.

**FR5-2.** Система должна изменять забытый пароль только после **обеих проверок**: правильного SMS-кода и правильного ответа на ранее заданный секретный вопрос.

**FR5-3.** Новый пароль должен соответствовать политике безопасности, а пользователь должен подтвердить его повторным вводом.

**FR5-4.** После успешного восстановления пароля система должна завершать прежние сессии пользователя, чтобы старые refresh-токены нельзя было использовать.

**FR5-6.** Система должна обеспечивать вход через Google и VK ID только при наличии ранее привязанной внешней учётной записи. Автоматическая регистрация нового пользователя через эти сервисы не предусмотрена.

# 7. Технические условия

## 7.1. Минимальные серверные требования

| СУБД                   | PostgreSQL                                                      |
| Развёртывание          | Контейнеризация допускается, Kubernetes необязателен для пилота |

## 7.2. Минимальные клиентские требования

| **Клиент** | **Условия использования**                                                     |
|------------|-------------------------------------------------------------------------------|
| Web        | Актуальные Chrome, Firefox, Edge или Safari, JavaScript и HTTPS               |
| Android    | Android 10+, соединение с сервером, локальная биометрия при наличии поддержки |
| iOS        | iOS 14+, соединение с сервером, локальная биометрия при наличии поддержки     |
| Для SMS    | Возможность получения SMS на зарегистрированный телефон                       |

## 7.3. Безопасность и устойчивость

- Пароли и секретные ответы должны храниться не в открытом виде, а в виде стойких хэшей (например, Argon2id).

- SMS-коды не должны попадать в ответы API, журналы и сообщения об ошибках в открытом виде.

- Срок SMS-кода предварительно принимается равным пяти минутам, между повторными отправками предлагается выдерживать не менее 60 секунд.

- При неуспешном вводе пароля, SMS-кода или секретного ответа должны действовать ограничения частоты запросов.

- Проверка подписи JWT не заменяет проверку действующей серверной сессии: необходимо учитывать выход из системы, блокировку и трёхминутное бездействие.

- Изменения ролей, выключение 2FA и другие чувствительные операции должны требовать актуальной аутентификации.

## 7.4. Производительность и надёжность (целевые показатели пилота)

Предварительно принимаются:

1\. p95 ответа GET /auth/profile не более 300 мс при 100 запросах/с

2\. p95 POST /auth/login без внешнего SMS не более 500 мс при 20 запросах/с

3\. Доля 5xx менее 1% на указанных испытаниях

4\. Для перспективной промышленной системы рассматривается доступность 99,9% в месяц при отказоустойчивом развёртывании

# 8. Тестирование и приемка

## 8.1. Виды проверок

- **Функциональные:** регистрация, SMS-подтверждение, вход, восстановление, работа ролей, ограничение устройств и управление сессиями.

- **Негативные:** неверный код, неверный пароль, занятый номер, блокировка, отсутствие прав, чужая сессия, повторное использование кода.

- **Контрактные:** соответствие путей, тел запросов, кодов и ответов действующей OpenAPI.

- **Интеграционные:** взаимодействие IdP, Verification Service, SMS-провайдера и защищённого backend, работа Google/VK ID для связанных учётных записей.

- **Безопасности:** подбор кода и пароля, отзыв сессии, попытки обойти блокировку и ограничения устройств.

- **Нагрузочные и совместимость:** замеры p95, RPS, 5xx, проверка поддерживаемых браузеров и мобильных ОС.

## 8.2. Основные приёмочные проверки

| **Код** | **Проверяемый результат**                                                                      |
|---------|------------------------------------------------------------------------------------------------|
| TC-01   | Незанятый номер подтверждается по SMS, после ввода данных появляется пользователь USER/ACTIVE. |
| TC-02   | Повторная регистрация номера не создаёт дубликат.                                              |
| TC-03   | Неверный код приводит к ошибке, после трёх ошибок попытка блокируется.                         |
| TC-04   | Использованный или неподтверждённый challenge_id нельзя применить к новой регистрации.         |
| TC-05   | Правильный телефон и пароль позволяют войти без 2FA, если она выключена.                       |
| TC-06   | При включённой 2FA токены выдаются только после правильного SMS-кода.                          |
| TC-07   | Для BLOCKED вход запрещён, для INACTIVE успешный вход восстанавливает ACTIVE.                  |
| TC-08   | Попытка подключить четвёртое устройство с отдельной активной сессией отклоняется.              |
| TC-09   | После трёх минут бездействия защищённый запрос и обновление токена отклоняются.                |
| TC-10   | Пользователь видит и завершает только собственные сессии.                                      |
| TC-11   | Пользователь USER не может менять роли и блокировать других; ADMIN может.                      |
| TC-12   | Восстановление пароля невозможно без SMS или без верного секретного ответа.                    |
| TC-13   | После восстановления прежние сессии недействительны.                                           |
| TC-14   | Внешний вход работает для ранее привязанной учётной записи и отклоняет непривязанную.          |
| TC-15   | API не раскрывает пароль, секретный ответ, одноразовый код и их хэши.                          |
| TC-16   | Выполняются проверки интерфейсов и нагрузочные испытания по разделу 7.                         |

# 9. Приложение

## 9.1. Перечень внешних API

Все URI ниже задаются относительно базового /api/v1.

| **Метод** | **Путь**                      | **Назначение**                                            |
|-----------|-------------------------------|-----------------------------------------------------------|
| POST      | /auth/register/start          | Создать SMS-попытку регистрации.                          |
| POST      | /auth/register/resend         | Повторно отправить регистрационный SMS-код.               |
| POST      | /auth/register/verify         | Проверить регистрационный SMS-код.                        |
| POST      | /auth/register/complete       | Создать пользователя после подтверждения.                 |
| POST      | /auth/login                   | Проверить телефон и пароль, при необходимости начать 2FA. |
| POST      | /auth/login/verify            | Подтвердить SMS-код входа.                                |
| POST      | /auth/logout                  | Завершить текущую сессию.                                 |
| POST      | /auth/refresh                 | Обновить токены.                                          |
| GET       | /auth/sessions                | Получить свои активные сессии.                            |
| DELETE    | /auth/sessions/{session_id}   | Завершить собственную сессию.                             |
| GET       | /auth/profile                 | Получить свой профиль.                                    |
| PATCH     | /auth/2fa                     | Изменить настройку 2FA.                                   |
| POST      | /auth/password/reset/start    | Отправить SMS для восстановления пароля.                  |
| POST      | /auth/password/reset/confirm  | Подтвердить SMS и секретный ответ, изменить пароль.       |
| POST      | /auth/oauth/exchange          | Войти через ранее привязанный Google/VK ID.               |
| PATCH     | /admin/users/{user_id}/role   | Изменить роль пользователя.                               |
| PATCH     | /admin/users/{user_id}/status | Заблокировать или разблокировать пользователя.            |
