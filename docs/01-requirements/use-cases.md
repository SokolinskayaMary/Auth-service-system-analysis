# Use Cases — система аутентификации и авторизации

## Назначение документа

В документе описаны основные варианты использования системы аутентификации и авторизации для веб- и мобильных приложений.

Каждый Use Case определяет участников, условия выполнения, основной сценарий, альтернативные сценарии и ожидаемый результат.

## UC-01. Регистрация нового пользователя

**Актор:** Новый пользователь.

**Цель:** Создать учётную запись для получения доступа к системе.

**Предусловия:**
- Пользователь находится на странице регистрации.
- Пользователь имеет доступ к номеру телефона, на который может получить SMS-код.

### Основной сценарий

1. Пользователь открывает страницу регистрации.
2. Система предлагает ввести номер телефона.
3. Пользователь вводит номер телефона и нажимает «Продолжить».
4. Система проверяет, что номер ещё не зарегистрирован.
5. Система отправляет SMS-код на указанный номер телефона.
6. Пользователь вводит полученный SMS-код.
7. Система проверяет правильность кода.
8. При успешном подтверждении система открывает форму регистрационных данных.
9. Пользователь вводит ФИО и дату рождения.
10. Система показывает секретный вопрос.
11. Пользователь вводит ответ на секретный вопрос.
12. Пользователь придумывает пароль.
13. Пользователь подтверждает регистрацию.
14. Система создаёт учётную запись, сохраняет хэш ответа на секретный вопрос, назначает роль `USER` и статус `ACTIVE`.
15. Система создаёт пользовательскую сессию и предоставляет доступ к приложению.

### Альтернативные сценарии

**А1. Номер телефона уже зарегистрирован.**

На шаге 4 система обнаруживает существующую учётную запись, сообщает об этом пользователю и предлагает перейти на страницу входа.

**А2. SMS-код не получен.**

На шаге 6 пользователь запрашивает повторную отправку кода. Система отправляет новый код с учётом ограничений частоты запросов.

**А3. SMS-код введён неверно.**

На шаге 7 система сообщает об ошибке и предлагает повторить ввод. После трёх неверных попыток проверка прекращается в рамках установленного ограничения.

### Постусловия

- Создана учётная запись пользователя.
- Номер телефона подтверждён.
- Хэш ответа на секретный вопрос сохранён.
- Пользователю назначены роль `USER` и статус `ACTIVE`.
- Создана пользовательская сессия.

**Связанная User Story:** US-01.

## UC-02. Вход в систему

**Актор:** Зарегистрированный пользователь.

**Цель:** Получить доступ к своей учётной записи.

**Предусловие:** Пользователь имеет уже зарегистрированную учётную запись.

### Основной сценарий

1. Пользователь открывает страницу входа.
2. Система предлагает ввести номер телефона и пароль.
3. Пользователь вводит данные и нажимает «Войти».
4. Система проверяет номер телефона, пароль и статус учётной записи.
5. Система проверяет количество подключённых устройств.
6. Если двухфакторная аутентификация включена, система отправляет SMS-код.
7. Пользователь вводит полученный SMS-код.
8. Система проверяет правильность кода.
9. После успешной аутентификации система создаёт сессию и выдаёт токены.
10. Пользователь получает доступ к приложению в соответствии со своей ролью.

### Альтернативные сценарии

**А1. Неверный номер телефона или пароль.**

На шаге 4 система сообщает об ошибке и предлагает повторить ввод данных.

**А2. SMS-код неверен.**

На шаге 8 система сообщает об ошибке. Пользователь может повторить ввод в пределах установленного лимита попыток.

**А3. Двухфакторная аутентификация отключена.**

После успешной проверки пароля и остальных условий система пропускает шаги 6–8 и завершает вход.

**А4. Учётная запись заблокирована (`BLOCKED`).**

Система отказывает во входе. Снять блокировку может только администратор.

**А5. Учётная запись неактивна (`INACTIVE`).**

Система разрешает пройти аутентификацию. После успешной проверки всех обязательных факторов статус пользователя меняется на `ACTIVE`.

**А6. Превышен лимит подключённых устройств.**

Система отказывает во входе с нового устройства и сообщает, что достигнут лимит трёх одновременно подключённых устройств.

### Постусловия

- Пользователь успешно аутентифицирован.
- Создана или обновлена его сессия.
- Выданы токены доступа.
- Пользователь получил доступ к разрешённым функциям.

**Связанная User Story:** US-02.

## UC-03. Восстановление пароля

**Актор:** Зарегистрированный пользователь, забывший пароль.

**Цель:** Установить новый пароль и восстановить доступ к учётной записи.

**Предусловия:**
- Пользователь ранее зарегистрирован в системе.
- При регистрации пользователь указал ответ на секретный вопрос.
- Пользователь имеет доступ к зарегистрированному номеру телефона.

### Основной сценарий

1. Пользователь открывает страницу входа.
2. Пользователь нажимает «Забыли пароль?».
3. Система предлагает ввести номер телефона для определения учётной записи.
4. Пользователь вводит номер телефона.
5. Система показывает секретный вопрос, установленный при регистрации.
6. Пользователь вводит ответ на секретный вопрос.
7. Система проверяет правильность ответа.
8. При успешной проверке система открывает форму установки нового пароля.
9. Пользователь вводит новый пароль и повторяет его для подтверждения.
10. Система проверяет совпадение паролей и соответствие требованиям безопасности.
11. Система сохраняет новый хэш пароля и завершает действующие пользовательские сессии.
12. Система уведомляет об успешном изменении пароля.
13. Пользователь может войти в систему с новым паролем.

### Альтернативные сценарии

**А1. Пользователь не помнит ответ на секретный вопрос.**

На шаге 5 пользователь выбирает «Не помню ответ на секретный вопрос».

1. Система предлагает восстановить пароль через подтверждение номера телефона.
2. Пользователь подтверждает отправку SMS-кода на указанный номер.
3. Система отправляет одноразовый SMS-код.
4. Пользователь вводит полученный код.
5. Система проверяет правильность кода.
6. При успешной проверке система открывает форму установки нового пароля.
7. Сценарий продолжается с шага 8 основного сценария.

**А2. Ответ на секретный вопрос неверен.**

На шаге 6 система сообщает об ошибке и предлагает повторить ввод в пределах установленного лимита попыток. Пользователь также может выбрать восстановление через SMS (А1).

**А3. SMS-код неверен или срок его действия истёк.**

На шаге 5 альтернативного сценария А1 система сообщает об ошибке. Пользователь может повторить ввод кода или запросить новый с учётом ограничений.

**А4. Новый пароль и подтверждение не совпадают.**

На шаге 9 основного сценария система сообщает об ошибке и предлагает повторить ввод пароля.

### Постусловия

- Пользователь успешно подтвердил свою личность одним из предусмотренных способов.
- Пароль учётной записи изменён.
- Предыдущие пользовательские сессии завершены.
- Пользователь может пройти повторную аутентификацию с новым паролем.

**Связанная User Story:** US-03.

## UC-04. Управление учётными записями

**Актор:** Администратор (`ADMIN`).

**Цель:** Управлять ролями пользователей, блокировать и разблокировать учётные записи.

**Предусловия:**
- Администратор успешно аутентифицирован.
- Администратор имеет необходимые права доступа.

### Основной сценарий

1. Администратор переходит в раздел управления пользователями.
2. Администратор выбирает учётную запись пользователя.
3. Система отображает доступные действия.
4. Администратор выбирает изменение роли или статуса учётной записи.
5. Администратор задаёт новое значение.
6. Система проверяет наличие необходимых прав.
7. Система применяет изменение.
8. Система уведомляет администратора об успешном выполнении операции.

### Альтернативные сценарии

**А1. Недостаточно прав.**

Система запрещает выполнение операции и сообщает об отсутствии необходимых разрешений.

**А2. Пользователь не найден.**

Система сообщает, что указанная учётная запись отсутствует.

### Постусловия

- Роль или статус выбранного пользователя изменён.
- Новые права или ограничения учитываются при последующих запросах.

**Связанная User Story:** US-04.

## UC-05. Вход через сторонний сервис

**Актор:** Зарегистрированный пользователь.

**Цель:** Войти в приложение через ранее привязанную учётную запись Google или VK ID.

**Предусловия:**
- Пользователь зарегистрирован по номеру телефона.
- Учётная запись стороннего сервиса ранее привязана к аккаунту пользователя.

### Основной сценарий

1. Пользователь открывает страницу входа.
2. Пользователь выбирает вход через Google или VK ID.
3. Система перенаправляет пользователя к выбранному провайдеру.
4. Пользователь проходит аутентификацию у провайдера.
5. Провайдер возвращает результат аутентификации.
6. Система проверяет результат и наличие привязки к существующему пользователю.
7. Система проверяет статус учётной записи и ограничения доступа.
8. При успешной проверке система создаёт сессию и выдаёт токены.
9. Пользователь получает доступ к приложению.

### Альтернативный сценарий

**А1. Учётная запись стороннего сервиса не привязана.**

Система отказывает во входе и сообщает пользователю, что необходимо использовать основной способ аутентификации.

### Постусловие

Пользователь вошёл в существующую учётную запись без автоматического создания новой.

**Связанная User Story:** US-05.
