# Архитектура системы аутентификации и авторизации

## 1. Назначение документа

Документ описывает логическую архитектуру системы аутентификации и авторизации для веб- и мобильных приложений.

Цель архитектуры — обеспечить централизованную регистрацию, аутентификацию, управление пользовательскими сессиями и проверку прав доступа при разделении ответственности между компонентами.

В документе рассматриваются логические компоненты и их взаимодействия. Физическая инфраструктура и развёртывание системы не проектируются.

## 3. Компоненты системы

### 3.1. Web UI/Mobile UI

Клиентские приложения предоставляют интерфейсы регистрации, входа, восстановления пароля и управления учётной записью.

Основные обязанности:

- Приём пользовательских данных.
- Отправка запросов к API.
- Отображение результатов операций и ошибок.
- Безопасная работа с выданными токенами.

Клиентские приложения не принимают окончательных решений о правах пользователя.

### 3.2. API Gateway

API Gateway — единая точка входа для клиентских HTTP-запросов.

Основные обязанности:

- Маршрутизация запросов к соответствующим компонентам.
- Ограничение частоты обращений (rate limitimg).
- Проверка подписи и срока действия JWT при обращении к защищённым ресурсам.
- Передача запросов во внутренние компоненты системы.

API Gateway не создаёт пользовательские сессии и не выпускает токены.

### 3.3. Registration Service

Registration Service управляет процессом создания новой учётной записи пользователя.

Основные обязанности:

- Инициирование регистрации по номеру телефона.
- Проверка существования пользователя через IdP.
- Организация SMS-подтверждения через Verification Service.
- Контроль успешного подтверждения телефона.
- Координация создания пользователя и первоначальной сессии.

После успешной регистрации новому пользователю назначаются роль `USER` и статус `ACTIVE`.

### 3.4. Verification Service

Verification Service отвечает за одноразовые SMS-коды.

Основные обязанности:

- Создание попыток подтверждения.
- Генерация и проверка кодов.
- Контроль количества попыток и срока действия кодов.
- Взаимодействие с внешним SMS-провайдером.

Механизм применяется при регистрации, двухфакторной аутентификации и резервном восстановлении пароля.

### 3.5. Identity Provider (IdP)

IdP — центральный компонент управления цифровой идентичностью пользователя.

Основные обязанности:

- Проверка учётных данных.
- Контроль статуса учётной записи.
- Управление пользовательскими устройствами и сессиями.
- Создание и обновление access- и refresh-токенов.
- Отзыв сессий.
- Обработка изменений пароля и настроек аутентификации.
- Управление ролями и статусами пользователей.
- Обработка входа через ранее привязанные Google и VK ID.

В проекте принято решение не создавать отдельные Token Service и Session Manager: соответствующие функции выполняет IdP.

### 3.6. Protected Backend

Protected Backend выполняет бизнес-операции, доступ к которым требует авторизации.

Перед выполнением защищённого действия необходимо проверить:

1. Результат проверки access-токена.
2. Наличие действующей пользовательской сессии.
3. Текущий статус учётной записи.
4. Наличие разрешения на запрашиваемое действие.

Проверка токена сама по себе не гарантирует право выполнить операцию.

### 3.7. PostgreSQL

PostgreSQL используется для хранения структурированных данных системы.

Основные группы данных:

- Пользователи и статусы учётных записей.
- Роли и разрешения.
- Устройства.
- Пользовательские сессии.
- Состояния SMS-подтверждений.
- Привязки внешних поставщиков аутентификации.

Пароли и ответы на секретные вопросы хранятся в виде защищённых хэшей. Refresh-токены не должны сохраняться в открытом виде.

## 4. Основные взаимодействия

### 4.1. Регистрация

1. Пользователь отправляет регистрационные данные через клиентское приложение и API Gateway.
2. Registration Service проверяет возможность регистрации номера.
3. Verification Service организует отправку и подтверждение SMS-кода.
4. После подтверждения номера Registration Service инициирует создание пользователя через IdP.
5. IdP создаёт учётную запись, сессию и токены.
6. Клиент получает результат успешной регистрации.

### 4.2. Аутентификация

1. Клиент отправляет телефон, пароль и сведения об устройстве.
2. IdP проверяет учётные данные, статус пользователя и ограничения по устройствам.
3. Если включена SMS-2FA, IdP инициирует дополнительную проверку через Verification Service.
4. После успешной аутентификации IdP создаёт сессию и выпускает токены.
5. Пользователь получает доступ к приложению.

### 4.3. Авторизация

1. Клиент обращается к защищённому API с access JWT.
2. API Gateway проверяет подпись и срок действия токена.
3. Защищённый backend проверяет актуальное состояние сессии, статус пользователя и разрешения его роли.
4. Если проверки успешны, операция выполняется.
5. При отсутствии необходимых прав доступ запрещается.

## 5. Основные ограничения

- Регистрация выполняется только по номеру телефона.
- Пользователь может иметь не более трёх одновременно подключённых устройств.
- После трёх минут бездействия серверная сессия считается завершённой.
- Учётная запись может находиться в состоянии `ACTIVE`, `INACTIVE` или `BLOCKED`.
- Блокировка и разблокировка выполняются администратором.
- Для управления доступом используется RBAC.
- Вход через Google и VK ID разрешён только для ранее привязанных учётных записей.
