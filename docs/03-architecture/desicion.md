# Архитектурные решения (Architecture Decision Records)

## Назначение документа

Документ фиксирует ключевые архитектурные решения, принятые при проектировании системы аутентификации и авторизации веб- и мобильных приложений.

Для каждого решения указаны контекст, выбранный подход, обоснование и последствия.

---

## ADR-001. Централизованная система аутентификации и авторизации

**Контекст**

Веб-приложение и мобильные приложения должны использовать единую учётную запись пользователя.

При независимой реализации аутентификации в каждом клиентском приложении возникает риск дублирования механизмов входа, хранения учётных данных и применения правил безопасности.

**Решение**

Выделить централизованную систему аутентификации и авторизации, к которой обращаются веб- и мобильные приложения.

Защищённые backend-сервисы используют результаты проверки личности пользователя и самостоятельно контролируют доступ к выполняемым операциям.

**Обоснование**

Централизация позволяет использовать общие правила регистрации, проверки учётных данных, управления сессиями и ролями.

**Последствия**

- Правила аутентификации сосредоточены в одной системе.
- Клиентские приложения не управляют учётными данными самостоятельно.
- Доступность централизованной системы становится важной для работы зависимых приложений.

## ADR-002. Использование API Gateway как единой точки входа

**Контекст**

Система включает несколько логических компонентов с различной ответственностью.

Клиентским приложениям необходим единый интерфейс взаимодействия с backend.

**Решение**

Использовать API Gateway для приёма и маршрутизации HTTP-запросов, ограничения частоты обращений и проверки подписи и срока действия JWT при обращении к защищённым API.

**Обоснование**

API Gateway позволяет централизовать общие инфраструктурные проверки, не дублируя их в каждом клиентском приложении.

**Последствия**

- Клиенты взаимодействуют с системой через единый API.
- Внутренние компоненты не обязаны предоставлять собственные публичные точки входа.
- API Gateway не заменяет IdP и не принимает окончательное решение о доступе к конкретной бизнес-операции.

## ADR-003. Разделение регистрации и SMS-подтверждения

**Контекст**

SMS-подтверждение используется не только при регистрации, но и при двухфакторной аутентификации и восстановлении пароля.

**Решение**

Выделить два логических компонента:

- **Registration Service** — управляет последовательностью регистрации и координирует создание учётной записи.
- **Verification Service** — создаёт и проверяет SMS-коды, контролирует попытки подтверждения и взаимодействует с SMS-провайдером.

Создание учётной записи выполняется через IdP после успешного подтверждения телефона.

**Обоснование**

Разделение позволяет повторно использовать механизм SMS-подтверждения в разных пользовательских сценариях.

**Последствия**

- Процесс регистрации зависит от работы Verification Service.
- Подтверждение должно быть привязано к конкретному `challenge_id`.
- Успешное подтверждение должно проверяться сервером при завершении регистрации, чтобы исключить повторное использование подтверждения.

## ADR-004. Управление сессиями и токенами внутри IdP

**Контекст**

Для аутентификации необходимо проверять учётные данные, создавать пользовательские сессии и выпускать access- и refresh-токены.

Рассматривалось выделение управления сессиями и токенами в отдельные компоненты.

**Решение**

Сосредоточить эти функции в Identity Provider (IdP), не выделяя самостоятельные Token Service и Session Manager.

**Обоснование**

Для текущего масштаба проекта такое разделение не является необходимым. Управление сессиями и токенами тесно связано с проверкой статуса пользователя и его учётных данных.

**Последствия**

- Уменьшается количество отдельных логических компонентов.
- IdP контролирует создание, обновление и отзыв пользовательских сессий.
- На IdP возлагается больше ответственности; при дальнейшем развитии системы может потребоваться пересмотреть его внутреннюю структуру.

## ADR-005. Серверная проверка сессий при использовании JWT

**Контекст**

Access JWT подтверждает факт выпуска токена и содержит срок его действия.

Однако при использовании только проверки подписи и `exp` невозможно немедленно учитывать завершение пользовательской сессии, выход из системы или блокировку учётной записи.

**Решение**

Использовать access JWT совместно с серверными сессиями.

При обращении к защищённому ресурсу система должна учитывать:

1. Корректность подписи и срок действия JWT.
2. Наличие действующей серверной сессии.
3. Актуальный статус учётной записи.
4. Необходимые разрешения пользователя.

Сессия завершается после трёх минут бездействия независимо от срока действия самого JWT.

**Обоснование**

Такой подход позволяет отзывать доступ до истечения срока действия токена.

**Последствия**

- Завершение сессии делает дальнейшие защищённые запросы недопустимыми, даже если JWT ещё не истёк.
- Проверка состояния сессии требует обращения к актуальным серверным данным.
- Дополнительные проверки могут увеличивать время обработки защищённого запроса.

## ADR-006. Использование ролевой модели RBAC

**Контекст**

Система должна разграничивать действия обычных пользователей и администраторов.

**Решение**

Использовать Role-Based Access Control (RBAC).

В текущем объёме проекта предусмотрены две роли: `USER` и `ADMIN`. Одному пользователю назначается одна роль.

Разрешения определяются отдельно от пользователей и связываются с ролями.

**Обоснование**

RBAC позволяет централизованно управлять доступом через назначение ролей, не создавая индивидуальный перечень разрешений для каждого пользователя.

**Последствия**

- Изменение роли влияет на доступные пользователю операции.
- Проверка прав выполняется на серверной стороне.
- Текущая модель ограничена одной ролью на пользователя. Поддержка нескольких ролей потребует изменения модели данных и правил авторизации.

## ADR-007. Выбор PostgreSQL для хранения данных

**Контекст**

Система хранит связанные данные пользователей, ролей, разрешений, сессий, устройств, SMS-проверок и внешних учётных записей.

Для этих данных важны ограничения целостности и согласованность изменений.

**Решение**

Использовать реляционную СУБД PostgreSQL.

**Обоснование**

PostgreSQL позволяет описать связи между сущностями через внешние ключи, контролировать уникальность данных и применять транзакции при выполнении связанных операций.

**Последствия**

- Модель данных строится на реляционных таблицах.
- Необходимо определить ограничения целостности и индексы.
- Операции создания сессий и контроля лимита устройств должны обеспечивать согласованное состояние данных.
- Отдельное NoSQL-хранилище в текущую архитектуру не включается.

## ADR-008. Два альтернативных способа восстановления пароля

**Контекст**

По результатам интервью пользователь должен иметь возможность восстановить пароль с помощью ответа на секретный вопрос.

Если ответ забыт, должен быть доступен резервный способ — подтверждение зарегистрированного номера телефона через SMS.

**Решение**

Предусмотреть два альтернативных способа подтверждения личности:

1. Правильный ответ на фиксированный секретный вопрос.
2. Правильный одноразовый SMS-код, отправленный на зарегистрированный номер.

Для изменения пароля достаточно успешного прохождения одного из этих способов.

В текущем API используются два endpoint: `/auth/password/reset/start` для резервного SMS-подтверждения и `/auth/password/reset/confirm` для установки нового пароля после соответствующей проверки.

**Обоснование**

Решение соответствует согласованным пользовательским сценариям и позволяет восстановить доступ при забытом ответе на секретный вопрос.

**Последствия и риски**

Восстановление по одному секретному ответу является менее защищённым механизмом, поскольку ответ может быть угадан, раскрыт или получен из других источников.

Для снижения риска необходимо ограничивать количество попыток, не раскрывать существование учётной записи через сообщения об ошибках и завершать прежние пользовательские сессии после изменения пароля.

Для промышленной реализации целесообразно дополнительно пересмотреть достаточность одного секретного ответа как доказательства личности.
